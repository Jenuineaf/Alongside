{% comment %} The comment thread on post detail — heading, form, list. {% include "social/_comment_section.html" %} Reads from the context, not from `with` params, because the three comment endpoints in social/views.py re-render this same fragment as their response: post the Post. comments a LIST (not a queryset — the length is rendered twice). comment_form a CommentForm. can_comment signed in and allowed to write (the public demo is not). `id="comment-section"` is the HTMX target for every change to the thread, and `#comments` is the anchor the feed card's comment icon links to. Both sit on this element; moving either breaks a link somewhere else. THE COUNT IN THE HEADING IS THE LENGTH OF THE RENDERED LIST, never `post.comment_count`. Those two legitimately disagree: counters are global (ADR-0002 — a viewer-relative count would leak how many comments a blocked person wrote), while this list is block-filtered. §7.2 resolves it by having post detail render what it fetched, so the heading always matches the rows underneath it. The denormalised number is for feed cards, which never appear on the same screen as the thread — and for the sticky bar's tally, which this fragment therefore updates out of band when the thread changes. Which is also why the thread is unpaginated (S13): page it, and "8 comments" sits above 8 of 40. {% endcomment %}
