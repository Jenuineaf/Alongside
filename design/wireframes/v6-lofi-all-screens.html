Greyscale boxes on purpose. The only question this document answers is: what data does each screen need to display or capture? Every box is annotated with the model field behind it. Fields that don't exist yet are marked MISSING. Written for the Architect's data-model review — the findings list is in docs/review/designer.md.

How to read this
  • Model.field — exists in data-model.md
  • MISSING — not in the schema
  • query — derived, not stored
  • Grey box = content · white box = input · dark box = button

GAP 1 — username User.username is unique, validated [a-z0-9_]{3,30}, reserved-blocklisted, and is the public URL (/u/<username>). The sign-up form doesn't ask for it. So either we ask (a fourth field + live availability check, which needs an endpoint) or we derive it from the email and let people change it later. §10 only describes derivation for Google sign-in; v1 is email/password.

Follow-on: is username changeable? If yes, old profile URLs rot and Settings needs a screen for it. Not answered anywhere.

GAP 2 — resume position Profile.onboarding_completed_at is null-or-set: it records finished, never how far. Someone who abandons on step 2 and comes back can't be resumed, and we can't tell "skipped everything" from "never started". GAP 3 — per-viewer annotations aren't specified anywhere Every card renders is_sparked and is_saved for the signed-in viewer. Neither is a field (correctly — they're PostSpark/SavedPost rows), but nothing in data-model.md says the feed query must annotate them. If each card checks individually that's an N+1 on the hottest query in the app. Needs to be a stated contract like .visible_to() is — e.g. Post.objects.for_viewer(user) adding both via Exists().
GAP 4 — tier provenance Home labels each band with where it came from ("from people you follow", "because you picked android"). The cascade is defined as three queries; nothing says the result carries a marker of which tier produced each post. Without it the bands can't be labelled and Home becomes an unexplained list — which is the whole cold-start problem. Cheap if Discovery returns tagged querysets; expensive to retrofit once the view is written.
Confirmed present: stale sinks rather than hides (is_stale as leading sort column), so the card needs a visual treatment for a stale-but-visible post. That's mine to design; the field exists.

GAP 8 — is a person's spark history public? I put a "Sparked" tab on other people's profiles. PostSpark has Index(user, -created_at), so it's queryable — but nothing says whether one user may see another's sparks. That's a privacy decision, not a schema one, and it needs an answer before the Social seat builds the tab. Safe default: sparks are public (they're a public signal that ranks the feed), saves are private. Confirm.

GAP 11 — conversation has no link to the idea it started from ⚠ biggest one The whole product is "find an idea → message the person". Anyone can DM anyone with no request gate, so the receiver's first question is always why is this person messaging me. Every screen I've drawn answers it with a context strip: "About: An app that moves leftover canteen food…"

Conversation has dyad_key, last_message_at, last_message_preview, created_at — and no reference to a Post. Suggested: origin_post = FK → Post, null=True, on_delete=SET_NULL. Nullable because profile-initiated DMs have no origin post, and SET_NULL so deleting the idea doesn't destroy the conversation.

This is cheap now and awkward later: retrofitting means either a migration with no back-fill possible, or dropping the feature.
GAP 12 — "You:" on the conversation preview The list shows whether the last message was mine. last_message_preview is text only; there's no last_message_sender. Joining to Message to find out defeats the point of denormalising the preview ("the list renders with zero joins"). Suggested: last_message_sender = FK → User, null, SET_NULL, written in the same transaction as the other two denormalised fields.
Covered: unread state from last_read_at; block hides the thread without deleting it; no read receipts or typing indicators in v1 (both Phase 2), so timestamps carry that weight.

GAP 13 — the stale-post nudge has no delivery channel ⚠ Spec §4.8 says a post untouched ~30 days "triggers 'Still looking for teammates?'". The schema has the trigger side (Post.is_stale, nudged_at, last_activity_at) but Notification.kind is exactly new_message / new_follower / new_comment. There is no way to put the nudge in front of the user in-app, and email is Phase 2. Either add a stale_nudge kind (plus the existing nullable post FK carries the target), or state that the nudge is surfaced only as a banner on the author's own post — in which case the author has to go looking for it, which defeats a nudge.
GAP 14 — follow notifications can't reach the note A new_follower row has actor but no link to the Follow row, so it can't render Follow.note — the single thing that makes a follow notification worth opening ("I'd want the Android role"). Workable without a schema change (look up Follow(follower=actor, following=recipient)), but that's an extra query per notification and it silently breaks if the follow is later withdrawn. A follow nullable FK would match the existing pattern of concrete nullable FKs per target type.
Covered: both dedup rules (§5.2), no spark notifications (Q9), and saved posts survive the post going team_formed — the Saved screen needs to show that state rather than hide the row.

Summary

15 findings. Three need a schema change before lock — GAP 11 (conversation → origin post), GAP 13 (no notification kind for the stale nudge), GAP 12 (last message sender). Two are decisions only Jeni can make — GAP 1 (username capture and changeability) and GAP 8 (are sparks public). Three are columns with no UI writing to them — GAP 5, 7, 9 — which are mine to design or the Architect's to cut. The rest are contracts and copy. Full write-up with severity: docs/review/designer.md.
